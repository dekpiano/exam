# Deep study completed 2026-09-24
- Routes are centralized in app/Config/Routes.php. Student pages: /, /lobby, /exam, /result. Student APIs: register, lobby/sync, exam/status, exam/start, exam/submit, exam/cheat, exam/log-error, exam/ai-grade. Teacher pages are all dashboard views: /teacher, /teacher/dashboard, /teacher/questions, /teacher/monitor, /teacher/results, /teacher/logs, /teacher/settings, /teacher/exam-settings, /teacher/manual. Teacher APIs cover auth, settings, exams CRUD/status/policy/mode, questions CRUD/import/image, results/grades, monitor and logs.
- Admin dashboard is a large single-page workspace; page routes mostly set activeTab/activeExamId and render the same admin/dashboard.php.
- Authentication: password login compares plaintext configured Admin Password from settings; Google login verifies tokeninfo, audience, expiry, issuer, @skj.ac.th domain, then looks up cross-database personnel record and learning area. Session stores teacher identity/image/learning.
- Authorization: checkAuth only checks admin_logged_in. Some exam/log endpoints filter teacher ownership by teacher_email, but not all mutation endpoints visibly perform ownership checks. This is a security area to inspect before exposing multi-teacher editing.
- Student registration: validates identity/email/exam; blocks Finished, enforces lobby_first, blocks prior cheating, counts exam_results against max_attempts, prevents duplicate student_code per exam, stores a single student row by email and session.
- Critical data-model behavior: StudentModel registration first searches by email only, then changes that row's exam_id when an existing email registers another exam. This means one student row can only represent one current exam; monitor/lobby behavior is therefore exam-session oriented rather than a historical registration table.
- startExam checks result count vs max_attempts, fetches all questions, randomly selects up to num_questions choice questions, includes all writing questions, shuffles choices and option order, and returns only client-safe question data (does not send correct_answer).
- Important integrity gap: selected question IDs/order are not persisted to exam_attempts in the current startExam flow. submitExam accepts client-provided question IDs/answers and re-reads questions from DB. The existing exam_attempts table is currently not integrated into the main attempt flow.
- submitExam grades choices server-side by exact case-insensitive text match against current correct_answer, writes writing as รอตรวจ, stores answer snapshot JSON, counts server-side suspicious logs, and inserts exam_results. It does not explicitly verify exam status is Started at submission time.
- exam page enforces waiting/finished redirects and calculates whole-exam timer from shared exams.started_at + exam_duration, meaning all students in an exam share the same global start clock when exam_duration is enabled.
- Result page uses the latest submitted result and determines pass status from choice score versus choice total * passing_percentage; writing points are displayed as waiting and not included in pass calculation.
- Admin results auto-repair can rewrite stored answers/score based on current question answers/points. This can change historical result scoring if a teacher edits a question after students have submitted.
- gradeResults handles manual writing scores and recomputes total; updateScoreDirect can directly change score and also clears cheating_flag/count, so this is a powerful administrative override.
- deleteExam deletes exam, questions, results and students manually, but current code does not visibly delete error_logs or exam_attempts for the deleted exam; orphan records are possible.
- updateExamStatus Started preserves existing started_at; Waiting clears started_at and deletes lobby students. saveExam similarly deletes lobby students when status Waiting.
- Database schema.sql is legacy/incomplete relative to current runtime. It lacks exams table entirely and later fields such as exam_id, student_code, exam_round, exam_duration, join_policy, anti_cheating, max_strikes, exam_mode. Runtime AdminController schema repair partially bridges this, while migration only creates exam_attempts. A canonical migration/schema reconciliation should be considered.
- UI: student exam page is a large custom CSS/JS application with sticky timer, progress, choice cards, writing textarea, anti-cheating controls, autosave/navigation behavior; result and login use Tailwind CDN + K2D. Admin dashboard is a large single-file SPA-like PHP/JS workspace.
- Main architecture strengths: clear student/teacher separation, server-side choice scoring, no correct answers sent to client, configurable exam lifecycle, Google school-account login, AI grading fallback, decimal score support, anti-cheating logs.
- Main technical risks identified: plaintext admin password; broad admin mutation surface with inconsistent teacher ownership enforcement; attempt/question snapshot not integrated; client can submit arbitrary question IDs and duplicated/omitted answers; submission status validation; shared global timer; historical score mutation from auto-repair; orphan cleanup; schema drift; possible single-email student row collisions across simultaneous exams; large monolithic dashboard/exam views.
